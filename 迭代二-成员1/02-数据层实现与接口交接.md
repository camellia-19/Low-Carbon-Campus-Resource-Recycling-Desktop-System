# 数据层实现与接口交接

成员1在既有Java17、JDBC、SQLite工程中完成数据层实现与验收。本轮沿用11张表及实体属性，不更改现有DAO、Service方法签名。以下约定用于成员2、3接入，也校正迭代一文档与实际代码的差异。

## 启动与重置

正常启动顺序如下，必须在业务线程开始前选择数据库：

```java
DbConfig.getInstance().applyToDbUtil();
DatabaseInitializer.initialize();
```

`initialize()`读取配置的种子开关；`initialize(false)`用于无演示数据的首次建库。初次建表和种子导入在同一事务内完成。旧库保留数据，不补导演示账号、不覆盖用户修改过的系统配置。

| 数据库状态 | 处理 |
|---|---|
| 不存在、空文件、没有业务表 | 创建11张表及索引，按开关导种子，登记结构版本1 |
| 旧版完整11表，版本0 | 检查必需列与外键，保留数据并登记版本1 |
| 当前版本1 | 校验并继续，不重建、不重新导种子 |
| 只有部分表或缺必需列 | 抛异常并保留原库，禁止自动删除补建 |
| 版本大于1 | 拒绝用旧程序打开，保留版本与数据 |

版本标记是 `PRAGMA user_version`，不是 `system_config.schema.version`。本轮只是对既有结构登记版本，没有改变表字段，也没有实现未来版本之间的通用迁移框架。旧库检查覆盖必需表、列与外键违规，不是所有历史约束定义的逐字比对。

仅当用户明确选择清空数据库时，调用：

```java
DatabaseInitializer.reset(true); // 清空当前URL的库并导入演示数据
```

reset不允许在业务事务内部执行；重建与种子导入发生异常时回滚。原 `schema.sql` 仍是显式重建脚本，手工运行会清空数据，不能作为日常启动命令。不要将正式库作为测试库。本轮没有在用户已有 `greencampus.db` 上执行重置。

成员3现有 `MainApp` 的 `--reset-db` 仍调用旧bootstrap入口，须由成员3按其建议文件接入新reset方法；否则该参数现在不会清空已有库。

## 配置与脚本资源

配置优先级为JVM `-D`参数、application.properties、内置默认值。示例：

```text
java -Ddb.url=jdbc:sqlite:data/campus.db -Dapp.seed.on.start=false ...
```

`DbConfig`为启动期单例，应在首次加载前指定JVM参数。测试直接 `DbUtil.init(临时库URL)`，然后调用initialize，避免重置全局部署参数。全局URL只允许在程序启动或测试串行准备阶段切换；不要在并行业务处理期间重配。

SQL读取先查配置的文件路径，再尝试Jar中的 `/db/schema.sql` 与 `/db/seed-data.sql`。本次未修改成员3负责的pom，当前Jar尚未内置这两个资源；Maven资源配置建议已经给成员3。迭代二数据层运行及测试仍可从工程目录读取 `../../db/`。

SQLite文件URL和共享内存URL均已测试。共享内存测试必须保持一条连接打开，例如 `jdbc:sqlite:file:uniqueName?mode=memory&cache=shared`，不能在多连接DAO测试中使用独立的 `jdbc:sqlite::memory:`。

## 事务与异常

```java
DbUtil.getInstance().executeInTransaction(conn -> {
    itemDao.updateStatus(itemId, "SOLD", null);
    tradeFlowDao.updateStatus(flowId, "DONE", null, finishedAt);
    // 同步监听器中的信用与日志DAO自动复用当前连接
    return null;
});
```

事务唯一入口是 `DbUtil.executeInTransaction`。`AbstractJdbcDao`只提供SQL执行、参数绑定、结果映射、连接释放与SQL异常转换，没有 `AbstractJdbcDao.executeInTransaction` 方法。原文档中该方法名及“所有异常统一变成TX-001”的说法应以这里为准。

- 外层事务负责连接、提交、回滚和ThreadLocal清理；内层调用复用外层连接，不自行提交。
- 嵌套事务失败会标记必须回滚。业务层即使catch后继续执行，外层也会拒绝提交并抛 `TransactionException`（TX-001）。
- DAO把SQLException转为 `DataAccessException`（DB-001）并标记必须回滚，保留根因。外层不会把已有AppException一律换码。
- 回调中的运行时异常和Error回滚后原样上抛；其他检查异常包装为TransactionException。
- 事务中的DAO不得关闭共享连接，事务外的DAO调用自行关闭其连接；每条连接开启外键与5000ms busy_timeout。
- 图片batchInsert本身是原子操作，可以独立调用，也可以参与发布事务。失败后回滚数据库记录；本轮没有代实现成员2、3的图片复制、压缩或文件清理逻辑。

不要吞掉业务失败后假报成功；如果捕获的是业务自定义异常且仍需使事务失效，可调用 `DbUtil.markRollbackOnly()`。数据层不自动重试整段业务，避免重复执行副作用。

## 查询与复用

User、Item、TradeFlow DAO使用long计算数据库offset；User和TradeFlow DAO每页最大100条。ItemQuery原有分页和查询状态语义属于共享DTO及业务层，本轮未代改，成员2应统一校验分页与默认公开状态。

排序仍经策略白名单选择，所有用户条件使用PreparedStatement参数绑定；系统配置以单条SQLite UPSERT消除先查后插的竞争窗口。

本轮实际实践的模式包括DbUtil/DaoFactory单例、DaoFactory工厂、AbstractJdbcDao模板方法；既有排序策略和事务内同步观察者继续复用。没有另建DAO实现或引入ORM/Spring。

原D2提到的“11个包”与当前源码不一致：现有含源码的包为根包、entity、dto、dao、dao.impl、service、service.impl、controller、ui、util、exception、config，共12个。部署配置由ConfigManager/DbConfig读取，数据库业务配置由SystemConfigDao读取。
