## M3-01 启动先应用数据库配置，再做结构初始化 优先处理

位置：`src/main/java/edu/campus/recycle/ui/MainApp.java`。

当前问题：没有调用 `DbConfig.getInstance().applyToDbUtil()`；`shouldInitialize`硬编码检查 `data/greencampus.db` 是否存在。自定义URL可能被忽略；零字节/不完整库虽然文件存在，仍跳过初始化，登录时才报无表错误。

成员1已把initialize改为保留数据的启动检查，现在建议每次正常启动执行：

```java
DbConfig.getInstance().applyToDbUtil();
appController.bootstrapDatabase(); // 内部initialize，现在不会清空已有数据
```

不要再按文件存在与否决定是否检查结构。初始化错误显示前先判断headless，避免用JOptionPane再次抛异常。正常桌面启动的UI操作仍放EDT，数据库访问保持在耗时任务中。

验收：首次启动建库；第二次用户数据仍在；空文件可建库；不完整库给明确错误且不覆盖；指定-Ddb.url后实际使用指定库。

## M3-02 显式重置需要接入新的reset入口 优先处理

当前 `--reset-db`仍调用bootstrap。由于成员1已将initialize改为非破坏操作，该参数现在不会清空已有数据。

请按参数分开调用：

```java
DbConfig.getInstance().applyToDbUtil();
if (resetRequested) {
    DatabaseInitializer.reset(DbConfig.getInstance().isSeedOnStart());
} else {
    appController.bootstrapDatabase();
}
```

只有明确请求清空才调用reset；建议在GUI给一次清空数据提示，日常启动不得重置。此处是实现建议，本次未改你的文件。

验收：普通启动保留新增用户与物品；明确重置后才还原演示数据。

## M3-03 打包时把SQL资源带入Jar

位置：pom.xml的build/resources。

成员1的初始化器已支持外部SQL不存在时查 `/db/schema.sql`、`/db/seed-data.sql`，当前pom未内置，仍只能从工程工作目录取 `../../db/`。可在保留原resources的前提下增加：

```xml
<resources>
  <resource><directory>src/main/resources</directory></resource>
  <resource>
    <directory>../../db</directory>
    <targetPath>db</targetPath>
    <includes>
      <include>schema.sql</include>
      <include>seed-data.sql</include>
    </includes>
  </resource>
</resources>
```

这段由你评审后加入。交付Jar前核实jar中确实包含两份SQL和application.properties，再从空目录运行测试；不要只在源码工程目录运行一次就认定可独立部署。

同时统一最终main.class和start.bat入口。当前控制台入口仍保留；成员1已将它改成只使用 `data/demo.db`，不再覆盖GUI的greencampus.db。

RegisterDialog用返回字符串的“注册成功”前缀判断业务状态。请和成员2对齐结构化结果或明确异常契约，再接真实页面；不要各自私改方法签名。

验收：JDK版本不符时有明确提示；真实编译错误返回非零；业务状态不靠展示文本解析。
